# V2.3 Control Dashboard

## Purpose

V2.3 adds a local human control plane over the certified V2.1 execution engine and V2.2 growth model. It does not create a second production engine.

```text
React browser UI
  -> localhost Control API
  -> thin control repository / review service
  -> V2.1 + V2.2 PostgreSQL truth
  -> immutable artifact storage / provider configuration
```

The UI contains only Overview, Brands, Productions, Review Queue and Providers.

## Existing contracts used

- `v2_1.productions`, `jobs`, `stage_runs` and `stage_definitions` provide execution truth.
- `artifacts`, `validation_results`, `v2_1.asset_registry` and immutable storage provide artifact truth where a safe production/brand relationship exists.
- `v2_2.brands`, products, audiences, offers, campaigns and versioned Brand Brain knowledge provide business context.
- the provider registry/gateway remains the only generation boundary; the dashboard only reports configuration and performs no paid probe.
- `MasterProductionOrchestrator` remains responsible for rendering and automated quality. A passing master can optionally register its immutable review evidence through `ControlReviewService`.
- publication remains owned by the existing publication gate/executor. Dashboard approval never invokes it.

## Why one migration is required

The previous schema cannot represent a durable human decision for an exact master:

- legacy `pipeline_runs.waiting_approval` has no master-version, reviewer or decision history;
- `v2_2.approval_policies` defines policy, not a human decision;
- `v2_1.publications` represents external delivery and must remain separate;
- the master orchestrator's `AWAITING_HUMAN_APPROVAL` value was returned in memory and its filesystem artifact metadata was not PostgreSQL review state.

`migrations/20260823_v2_3_control_reviews.sql` therefore adds only:

- immutable `v2_3.master_review_items`, tied to workspace, brand, production, artifact ID, reported artifact version, immutable storage key and content hash;
- append-only `v2_3.master_review_decisions`, with one terminal decision per exact review item.

The current ArtifactService reports version `1` for deterministic idempotency paths. Therefore storage key and content hash are also part of exact version identity: an approved V1 does not approve a later V2 at a different immutable key. The migration does not alter V2.1 production, retry, lease, stage, artifact or publication contracts.

Queue membership is derived from durable truth: a registered immutable master with `PASS` validation evidence and no terminal decision. There is no dashboard-only waiting flag.

Concurrent decisions lock the review item in PostgreSQL. The first terminal decision wins; a duplicate identical decision is idempotent, while a conflicting decision returns HTTP `409`. Decision rows cannot be updated or deleted.

## Development setup

Requirements: Node.js 22, PostgreSQL with V2.1/V2.2 migrations, and access to the same artifact storage root used by production.

Apply the new migration to a development database:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/20260823_v2_3_control_reviews.sql
```

This command is not authorization for a production migration. Production migration still requires explicit human approval and normal backup/recovery procedures. The migration is forward-only: recovery is to fix the failed statement and rerun the idempotent migration; review history must not be dropped.

Configure `.env`:

```text
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/content_os
CONTENT_FACTORY_STORAGE_ROOT=/absolute/path/to/content-factory-artifacts
DASHBOARD_ACTOR=local-operator
DASHBOARD_API_HOST=127.0.0.1
DASHBOARD_API_PORT=3001
```

Start both API and Vite:

```bash
npm install
npm run dashboard:local
```

The local runner uses the same placeholder-safe Docker/database discovery as `live:production:local`, prefers `content_os`, uses `~/.content-factory/storage` unless explicitly configured, verifies the V2.1/V2.2/V2.3 tables, and refuses occupied API/web ports before launching. It never prints database credentials. Use `npm run dashboard` only when a real reviewed `DATABASE_URL` and storage root are already supplied explicitly.

On success it prints the final dashboard and API URLs. Defaults are `http://127.0.0.1:3000` and `http://127.0.0.1:3001`. Override them with `DASHBOARD_WEB_HOST`, `DASHBOARD_WEB_PORT`, `DASHBOARD_API_HOST`, and `DASHBOARD_API_PORT`.

## Control API

```text
GET  /api/health
GET  /api/overview
GET  /api/brands
GET  /api/brands/:brandId
GET  /api/productions?brandId=&status=
GET  /api/productions/:productionId?brandId=
GET  /api/productions/:productionId/stages?brandId=
GET  /api/productions/:productionId/artifacts?brandId=
GET  /api/reviews?brandId=&history=false
POST /api/reviews/:reviewItemId/approve
POST /api/reviews/:reviewItemId/reject
GET  /api/providers
GET  /api/artifacts/:artifactId/versions/:version/content?sourceId=&brandId=
```

Decision bodies carry `brandId`; rejection also requires `reason`. The server obtains actor identity from `DASHBOARD_ACTOR`. Every decision and artifact lookup proves workspace/brand/production ownership in persisted relationships. IDs, filters and body size are validated. Artifact storage keys are never sent to the browser and are resolved only through the path-safe storage adapter.

## Security assumptions

The MVP binds to localhost, has no remote authentication and must not be exposed to a network. Remote deployment requires authentication, authorization, TLS and a reviewed operator identity model. Provider keys are never returned. Provider availability is configuration-derived and does not call provider APIs.

## Supported and intentionally absent

Supported: live overview, brand detail, production/stage/artifact inspection, browser-readable scoped media, exact-master review, provider routing visibility.

Not implemented: New Production, Regenerate, publishing, analytics, opportunities, learning UI, secret editing, auth, deployment or autonomous spending. New Production and Regenerate remain absent because the core has no safe reusable command boundary for them.
