# V2.1 Publish Execution

Publication is the controlled production boundary after the publication readiness gate.

## Production model

`Artifact Version → Validation → Readiness Gate → Publication Intent → Publisher Adapter → External Destination`

The publication layer owns execution state and idempotency. It does not mutate the artifact or validation record.

## Durable identity

Every publication has a deterministic `publication_key`. The key is persisted in `v2_1.publications` with a database uniqueness constraint. Provider adapters must forward the same key when the destination supports idempotency.

## Lifecycle

- `PENDING`: publication intent exists but execution has not started;
- `PUBLISHING`: one worker owns the active publication attempt;
- `PUBLISHED`: destination accepted the publication and the result is recorded;
- `FAILED`: the attempt failed and may be retried by the execution policy.

An already `PUBLISHED` key is reused. An active `PUBLISHING` key is not executed a second time. This prevents duplicate side effects under concurrent workers.

## Gate

A publication request without an allowed readiness decision fails with `PUBLICATION_BLOCKED` and never reaches the publisher adapter.

## Failure semantics

The publisher receives the stable idempotency key. This is essential for the crash window between an external side effect and recording `PUBLISHED`: a retry must be safe at the destination, not merely inside the process.

## Certification

The deterministic certification covers:

- allowed publication;
- stable idempotency key propagation;
- duplicate request reuse;
- in-flight duplicate suppression;
- failure state recording;
- blocked publication never reaching the publisher.

Provider-specific credentials, transport, rate limits, retries, reconciliation, and destination APIs remain outside this contract.
