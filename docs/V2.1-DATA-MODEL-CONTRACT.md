# V2.1 Data Model Contract

## Status

This document captures the canonical target boundaries for the V2.1 data model. It is a design contract and does not authorize casual changes to certified execution functions or PostgreSQL recovery/concurrency logic.

## 1. Canonical ownership model

```text
Workspace
  |
  +-- Pipeline Run
        |
        +-- Job Stage
        |     |
        |     +-- Stage Attempt(s)
        |     +-- Artifact Version(s)
        |     +-- Validation Result(s)
        |
        +-- Production context / inputs
```

Execution state and production data remain separate.

- `pipeline_runs` = lifecycle of one production execution.
- `job_stages` = deterministic lifecycle units inside that execution.
- `stage_attempts` = execution history for one logical stage.
- artifacts = production outputs, not worker state.
- validation results = evidence about an artifact/output, not the artifact itself.

## 2. Artifact model

The target model is:

```text
artifact
  = logical artifact identity

artifact_version
  = immutable content version
```

A version is immutable after creation. Regeneration creates a new version and never overwrites an existing version.

Where compatibility fields still exist, they remain transitional until a dedicated normalization migration is certified.

## 3. Provenance

Provider and model provenance belongs to the artifact version because different versions may be produced by different providers/models.

Canonical relationship:

```text
artifact -> artifact_version -> provider/model
```

## 4. Stage/artifact relationship

A stage may produce zero, one, or multiple artifacts depending on the stage.

Examples:

- SCRIPT -> one script artifact
- SHOT_PLAN -> shot-plan artifact plus structured shot records
- ASSET_PLAN -> asset-plan artifact plus asset requirements
- ASSETS -> multiple asset artifacts
- VALIDATION -> validation records referencing artifact versions

The data model must not assume a stage can have only one output artifact.

## 5. Validation

Validation is evidence, not mutable artifact state.

Canonical target:

```text
artifact_version
      |
      +-- validation_result(s)
```

Existing compatibility linkage may remain until a dedicated migration introduces direct immutable-version references.

## 6. Idempotency

Idempotency has separate scopes:

- Pipeline: `(workspace_id, idempotency_key)`
- Stage: logical stage within a pipeline
- Asset requirement: requirement-level key
- Provider attempt: unique `(stage_id, attempt_no)`
- Artifact version: unique version within its logical artifact

Keys identify the intended logical operation, not a worker invocation.

## 7. Retry model

A retry creates another `stage_attempts` row while preserving the same logical `job_stages` row.

```text
stage
  +-- attempt 1 -> failed
  +-- attempt 2 -> failed
  +-- attempt 3 -> completed
```

The logical stage is the durable unit; attempts are execution history.

## 8. Continuity model

`continuity_snapshots` are historical snapshots, not mutable master records. A snapshot freezes the exact state used by a production stage/scene/shot.

The `state_hash` is the integrity identifier for snapshot content.

## 9. Legacy data

Legacy execution records must remain traceable during migration compatibility. V2 migrations must not silently rewrite or delete legacy production records.

The long-term target is:

```text
legacy execution records
        |
        +-- migration compatibility

V2 pipeline_runs / stages / attempts / artifacts
        |
        +-- canonical production execution
```

## 10. Provider model

Provider identity/configuration remains separate from stage state.

`provider_capabilities` describes routing capability and priority. Execution records which provider/model was actually used.

NVIDIA remains the first text-generation provider.

## 11. Canonical stage vocabulary

The production lifecycle is:

`SIGNAL -> IDEA -> BRIEF -> BIBLE -> CONCEPT -> SCRIPT -> SHOT_PLAN -> ASSET_PLAN -> ASSETS -> EDIT -> PLATFORM_ADAPTATION -> VALIDATION -> PUBLISH -> ANALYZE -> LEARN`

Older prototype names must be explicitly mapped if retained for compatibility.

## 12. Deletion and retention

Production history should be append-oriented.

- Artifact versions are immutable.
- Validation evidence should survive according to retention policy.
- Production deletion/cascade semantics must be explicit.
- Legacy records must not be deleted by V2 migrations.

## 13. Follow-up normalization

A future controlled schema migration may:

1. make `artifacts` the logical artifact table;
2. make `artifact_versions` authoritative for immutable versions;
3. move provider/model provenance to artifact versions;
4. add direct artifact-version references to validation;
5. add explicit stage/output cardinality support;
6. strengthen continuity-to-production-version traceability;
7. define production retention semantics;
8. add database assertions for the new invariants;
9. update tests before changing production worker behavior.

Any such migration must be implemented and certified independently; this document is not itself a schema change.
