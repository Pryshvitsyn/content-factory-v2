# V2.1 Data Model Contract

## Purpose

This document defines the canonical data-model boundaries for V2.1 before the worker and provider layers are expanded. It is a design contract, not a request to modify the currently certified execution functions.

## 1. Canonical ownership model

```text
Workspace
  |
  +-- Pipeline Run
        |
        +-- Job Stage
        |     |
        |     +-- Stage Attempt(s)
        |     |
        |     +-- Artifact Version(s)
        |     |
        |     +-- Validation Result(s)
        |
        +-- Production context / inputs
```

Execution state and production data remain separate.

- `pipeline_runs` = lifecycle of one production execution.
- `job_stages` = deterministic lifecycle units inside that execution.
- `stage_attempts` = provider/execution attempts for one logical stage.
- artifacts = production outputs, not worker state.
- validation results = evidence about an artifact/output, not the artifact itself.

## 2. Artifact model — decision

The current migration contains both `artifacts.version` and `artifact_versions.version`. This is redundant and creates two competing interpretations of version identity.

### Canonical target

`artifacts` should represent the **logical artifact identity**.

`artifact_versions` should represent the **immutable content versions**.

Conceptually:

```text
artifact
  id
  workspace_id
  logical_key
  artifact_type
  current_version_id (future)
  created_at

artifact_version
  id
  artifact_id
  version
  content / uri
  sha256
  provider_id
  model_id
  metadata
  created_at
```

A version is immutable after creation. Regeneration creates a new version; it never overwrites an existing version.

### Transitional rule

Do **not** change the existing tables while PostgreSQL execution certification is running. The existing schema remains the compatibility baseline. A dedicated follow-up migration should normalize this model after certification.

## 3. Provenance

Provider and model provenance belongs to the artifact version because different versions may be produced by different providers/models.

Therefore the long-term canonical relationship is:

```text
artifact -> artifact_version -> provider/model
```

The existing provider/model columns on `artifacts` are transitional compatibility fields and should not become the authoritative provenance source.

## 4. Stage/artifact relationship

A stage may produce zero, one, or multiple artifacts depending on the stage.

Examples:

- SCRIPT -> one script artifact
- SHOT_PLAN -> one shot-plan artifact plus structured shot records
- ASSET_PLAN -> one asset-plan artifact plus asset requirements
- ASSETS -> multiple asset artifacts
- VALIDATION -> validation records, normally referencing artifact versions

Therefore artifact cardinality must not be encoded as a single `output_artifact_id` assumption at the data-model level. `job_stages.output_artifact_id` may remain as a compatibility/convenience pointer, but it must not be the sole representation of stage outputs.

## 5. Validation

Validation is evidence, not mutable artifact state.

Canonical target:

```text
artifact_version
      |
      +-- validation_result(s)
```

A future migration should allow validation to point directly to an immutable artifact version. Existing `artifact_id` linkage remains compatible during transition.

## 6. Idempotency

Idempotency has different scopes and must not be collapsed into one global concept.

- Pipeline idempotency: `(workspace_id, idempotency_key)`
- Stage idempotency: logical stage within a pipeline
- Asset requirement idempotency: requirement-level key
- Provider attempt: unique `(stage_id, attempt_no)`
- Artifact version: unique version within its logical artifact

Idempotency keys must identify the intended logical operation, not a worker invocation.

## 7. Retry model

A retry creates another `stage_attempts` row while preserving the same logical `job_stages` row.

```text
stage
  +-- attempt 1 -> failed
  +-- attempt 2 -> failed
  +-- attempt 3 -> completed
```

The logical stage is therefore the durable unit; attempts are execution history.

A dead-letter record represents terminal failure handling and must preserve enough context to safely inspect or requeue the failed logical operation.

## 8. Continuity model

`continuity_snapshots` are historical snapshots, not mutable master records.

The existing character/location records remain source data. A snapshot freezes the exact state used by a production stage/scene/shot.

The `state_hash` is the integrity identifier for the snapshot content.

A future migration should strengthen the relationship between snapshot and the exact artifact/stage version that consumed it, rather than relying only on script/scene/shot references.

## 9. Legacy data

Legacy `generation_jobs` remain the source system during migration compatibility.

V2 records created from legacy jobs must be traceable through `source_job_id` and migration metadata.

No migration should silently rewrite or delete legacy production records.

The long-term target is:

```text
legacy generation_jobs
        |
        +-- migration compatibility

V2 pipeline_runs / stages / attempts / artifacts
        |
        +-- canonical production execution
```

The legacy layer can be retired only after all production paths have moved to the V2 contract.

## 10. Provider model

`ai_providers` and `ai_models` remain provider identity/configuration sources.

`provider_capabilities` describes what a provider can do and its routing priority.

Provider configuration must not be embedded into stage state. Stage execution records which provider/model was actually used; routing policy remains provider configuration.

NVIDIA remains the first text-generation provider.

## 11. Naming contract

The canonical production stage vocabulary must be one vocabulary across:

- database rows
- worker contracts
- tests
- artifacts
- documentation
- provider adapters

The production lifecycle is:

`SIGNAL -> IDEA -> BRIEF -> BIBLE -> CONCEPT -> SCRIPT -> SHOT_PLAN -> ASSET_PLAN -> ASSETS -> EDIT -> PLATFORM_ADAPTATION -> VALIDATION -> PUBLISH -> ANALYZE -> LEARN`

Older prototype names such as `production_bible` or `shots` must not silently become alternative canonical stage identities. If retained for legacy compatibility, they must be explicitly mapped.

## 12. Deletion policy

Production history should be append-oriented.

- Artifact versions: immutable; never cascade-delete historical versions merely because an execution record is removed.
- Validation: should survive long enough to preserve audit evidence.
- Pipeline/stage records: may use cascade semantics for temporary/test data, but production retention policy should be explicit.
- Legacy records: must not be deleted by V2 migration.

The current migration uses several `ON DELETE CASCADE` relationships. These should be reviewed before the production retention policy is finalized.

## 13. Follow-up migration plan

After execution certification, the next schema migration should be a controlled normalization migration with these goals:

1. Make `artifacts` the logical artifact table.
2. Make `artifact_versions` the authoritative immutable version table.
3. Move provider/model provenance to artifact versions.
4. Add direct artifact-version references to validation results.
5. Preserve compatibility fields temporarily where required.
6. Add explicit stage/output cardinality support.
7. Strengthen continuity-to-production-version traceability.
8. Define production retention/deletion semantics.
9. Add database assertions for all new invariants.
10. Update tests before changing the production worker.

## Current decision

**Do not implement the normalization in the current execution-certification commit.**

The current branch is intentionally kept stable while PostgreSQL 17 execution/concurrency certification runs. This document captures the target contract so the next schema change is deliberate rather than incremental drift.
