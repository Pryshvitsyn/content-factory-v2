# V2.8.1 canonical spoken-copy and validation contract

V2.8.1 is a compatibility-preserving correction to the V2.8 provider-neutral production path. It does not change publication, certification, artifact immutability, brand scope, or provider fallback policy.

## Canonical spoken copy

`approvedSpokenCopy` is the single authoritative spoken narrative.

- If the operator supplies `voiceover`, its trimmed value is authoritative and is not rewritten.
- Otherwise the authoritative value is `hook + coreMessage + CTA`.
- Scene spoken-copy segments are deterministic partitions of the authoritative value. Joining their normalized token sequences must reproduce the authoritative normalized token sequence exactly and in order.
- The planned voice asset text is the authoritative value.
- `spokenCopyPolicy.strictApprovedCopy=true` rejects both missing approved tokens and injected unapproved tokens.
- Punctuation, whitespace, and scene-boundary changes are non-semantic. Token order and token identity are semantic.
- Hook and CTA are editorial requirements checked against `approvedSpokenCopy`; they are not reconstructed from scene positions.

Default copy distribution is one scene for the full narrative, two scenes with the core divided across both sides, three scenes for hook/core/CTA, and four or more scenes with the core divided once across the middle scenes. The full core message is never copied into every middle scene.

Existing V2.5/V2.6 raw inputs remain readable. When they lack the versioned fields, the voice asset text (or scene dialogue when speech is disabled) supplies the compatibility value, and their legacy fingerprint calculation is preserved. New operator inputs persist the additive `approved_spoken_copy` and `spoken_copy_policy` fields.

## Validation phases

Pre-execution validation runs during PREPARE/PREFLIGHT and again inside `MasterProductionOrchestrator.build` before the first provider execution. Failure is fail-closed with provider executions equal to zero.

The deterministic phase checks:

- approved spoken copy, hook, and CTA;
- ordered scene copy distribution;
- exact planned speech copy under strict policy;
- voice asset cardinality;
- shot-to-scene and shot-to-asset references;
- scene/shot timing;
- buildable master structure and one primary visual per shot;
- continuity;
- explicit provider/model plans for paid assets;
- explicit final delivery profile.

Post-render validation is limited to facts that require rendered output:

- final width and height;
- final frame rate;
- final duration;
- video stream/codec presence;
- required audio stream presence.

Each check records `code`, `status`, a safe `message`, and `details.actual`/`details.expected`. Combined validation embeds both `preExecution` and `postRender` evidence.

## Provider generation vs final delivery

Provider generation settings describe source media and remain provider/model/profile specific. They may, for example, request 720p at 24fps.

`FINAL_MASTER_DELIVERY_PROFILE` is the canonical FFmpeg output contract and remains 1080×1920 at 30fps. Final validation uses this delivery profile, never the provider source profile.

## Durable lifecycle and operator visibility

Post-render failure evidence is stored in the existing durable job `error` JSONB contract with status, score, checks, validation class, timestamp, and immutable master identity. This is an additive JSON contract, so no database schema migration is required. The Dashboard also reads the prior `error.details.quality` representation so historical V2.8 failures remain visible without mutating their records.

When a master was assembled and validation failed, the operator lifecycle is:

1. Planning — completed
2. Provider Generation — completed
3. Master Assembly — completed
4. Validation — failed
5. Human Review — blocked

A passing validation moves Human Review to `AWAITING_HUMAN_APPROVAL`. Auto-publish remains disabled.
