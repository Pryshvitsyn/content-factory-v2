# V2.1 Artifact Architecture

## Purpose

Define the canonical artifact model before implementation changes. This document intentionally does not modify worker execution functions.

## Core model

```text
Production
   |
  Stages
   |
 Attempts
   |
 Artifact
   |
 Artifact Version
   |              \
Validation       Storage
                    |
                 actual file
```

These are relationships, not a requirement that every stage produces exactly one artifact.

## 1. Artifact = logical identity

An artifact represents a durable logical output of the factory.

Examples:

- `script`
- `production_bible`
- `shot_plan`
- `asset_manifest`
- `video`
- `export`

An artifact is not the binary payload itself and is not a mutable file pointer.

## 2. Artifact Version = immutable result

Every material change creates a new immutable version.

```text
SCRIPT-1042
  v1 -> rejected
  v2 -> approved
  v3 -> approved revision
```

A version must retain the content identity (hash), size/type metadata, creation time, and provenance needed to reproduce or audit the result.

Versions are never overwritten in place.

## 3. Provenance

Provenance belongs to the artifact version because different versions may be generated by different providers/models.

Minimum provenance concepts:

- provider
- model
- provider request/correlation ID when available
- generation parameters
- input/context reference
- created timestamp
- application/pipeline/stage identity

The core artifact model must not depend on NVIDIA-specific request fields.

## 4. Validation

Validation is attached to the immutable artifact version being evaluated.

A validation record should identify:

- artifact version
- validation type/rule set
- result/status
- score where applicable
- structured findings
- validator version
- timestamp

A later artifact version does not silently inherit a previous validation result. It may reference or compare with prior versions, but it must be independently validatable.

## 5. Stage relationship

A stage is an execution context. A stage may produce zero, one, or many artifacts.

Therefore a single `output_artifact_id` is insufficient as the canonical production relationship for multi-output stages.

The target relationship is an explicit stage-output association that can record:

- stage
- artifact
- role/key (for example `primary_script`, `shot_plan`, `thumbnail`)
- ordinal when ordering matters
- created-at / attempt context

This association can be introduced without changing certified claim/lease execution.

## 6. Storage relationship

PostgreSQL stores artifact/version metadata and the storage address. Large payloads remain outside PostgreSQL.

```text
Artifact Version
  -> content_hash
  -> byte_size
  -> mime_type
  -> storage_backend
  -> storage_key

Storage backend
  -> actual video/image/audio/file
```

The application must not hard-code a Windows path. The storage backend is an abstraction.

## 7. Idempotency and immutability

The same logical stage execution must not overwrite an existing immutable version.

If a stage is retried and produces a different result, the result becomes a new version/attempt outcome according to the execution policy.

Content hashes provide integrity and support deduplication checks, but hash equality must not erase provenance or validation history.

## 8. Canonical artifact types

The initial controlled vocabulary is:

- `script`
- `production_bible`
- `shot_plan`
- `asset_manifest`
- `video`
- `export`

Additional types must be added deliberately rather than through arbitrary strings scattered through workers.

## 9. Migration strategy

Do not immediately delete legacy columns or rewrite execution code.

Migration sequence:

1. document the canonical model;
2. add explicit stage-output association;
3. project existing artifact/version data into the canonical relationship;
4. project validation rows to immutable versions;
5. verify historical data;
6. only then deprecate redundant legacy fields.

The certified execution foundation remains unchanged during this architecture step.
