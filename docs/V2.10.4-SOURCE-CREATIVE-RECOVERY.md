# V2.10.4 Source Creative Recovery

## Root cause

The source-quality recovery classifier distinguished objective media geometry failures and cross-shot continuity failures, but it did not distinguish a semantic `CREATIVE_PLAN_MISMATCH` from evidence-only failures. A technically valid clip that visibly contradicted its approved creative plan could therefore fall through to `RE_EVALUATE_EXISTING_ASSET`. Re-evaluating immutable bytes cannot change the depicted content.

V2.10.4 classifies only the verified quality-contract code `CREATIVE_PLAN_MISMATCH` as `SOURCE_CREATIVE`. Validator thresholds and FAIL dispositions are unchanged.

## Recovery contract

`SOURCE_CREATIVE` is available only when durable source-quality evidence identifies exactly one failed asset and that asset contains a semantic FAIL with code `CREATIVE_PLAN_MISMATCH`. Brand ownership, production identity, failed-job identity, and external-execution reconciliation are checked before a proposal is offered.

The recovery lifecycle is:

1. Preserve the rejected source artifact and quality evidence immutably.
2. Present a zero-call preflight for one video generation and one fresh semantic evaluation (maximum two external calls).
3. Require explicit operator confirmation.
4. Create one new immutable shot revision with a new asset identity, fingerprint, provider idempotency identity, artifact version, content hash, provider request ID, and source lineage.
5. Inject the canonical corrective constraint into the replacement asset's actual generation prompt while retaining the approved creative plan as authoritative.
6. Run normal decoding, geometry, deterministic, temporal, composition, and semantic source validation on the new replacement bytes.
7. If validation fails, mark the bounded recovery failed and stop. There is no automatic second replacement.
8. Only after PASS, record the replacement as accepted and atomically move the exact failed job to `RETRYING` with `sourceRecovery` evidence.
9. Require the operator to select **CONTINUE SAME EXECUTION**. The resumed execution substitutes the accepted replacement for the rejected source and runs only incomplete downstream work.

## Immutable lineage and one-attempt rule

The original `video-1` artifact remains addressable by its original artifact ID, version, storage key, and content hash. `shot_regenerations` records `SOURCE_CREATIVE`, `CREATIVE_PLAN_MISMATCH`, the superseded source asset, and automatic attempt 1. A partial unique index permits only one automatic creative recovery record for a production/source-asset pair. Failed or unvalidated revisions are never eligible replacement sources.

The migration is forward-only. Disabling the application route does not remove historical failure evidence, provider executions, artifacts, or accepted replacement lineage.

## Cost and call boundary

Recovery preflight performs no provider or evaluator calls. It reports:

- new video generations: 1;
- fresh semantic evaluations: 1;
- maximum external calls: 2;
- failed artifact: preserved immutably;
- good assets: reused;
- same production: yes;
- human approval: required;
- auto-publish: false;
- cost: known values where registered, otherwise `UNKNOWN`.

Deterministic rejection stops before semantic evaluation where the normal evaluator contract permits it. No automatic retry loop exists.

## Dashboard behavior

The existing Safe Recovery panel identifies **CREATIVE PLAN MISMATCH**, recommends **REGENERATE FAILED SHOT · 1 VIDEO**, shows the bounded accounting and immutable-history guarantees, and requires explicit confirmation. It never recommends standalone semantic re-evaluation for this failure. After accepted replacement validation, it exposes **CONTINUE SAME EXECUTION**.

## Operator procedure for the verified production

For production `067bd316-ee7c-42c8-bea3-ae61f72847b1` and job `bb4aff78-a7f8-4b8b-9405-b3957644104e`:

1. Open **Productions → V2.10.4 Safe Recovery** and verify source `video-1`, recovery kind `SOURCE_CREATIVE`, maximum external calls 2, human approval required, and auto-publish false.
2. Select **REGENERATE FAILED SHOT · 1 VIDEO**.
3. Review the provider/model, cost status, canonical opening-distance/no-contact instruction, and immutable-history notice.
4. Explicitly confirm the one paid replacement attempt.
5. Wait for replacement generation and fresh source-quality evaluation. If it fails, stop and inspect the durable failure; do not trigger an automatic second attempt.
6. When the panel reports `READY_TO_CONTINUE`, verify the production and job IDs are unchanged.
7. Select **CONTINUE SAME EXECUTION** and explicitly confirm its separate remaining-work preflight.
8. Let shots 2–3, missing voice, continuity evaluation, master assembly, final quality, and mandatory human review proceed normally. Auto-publish remains false.

No real regeneration is performed by installing or testing V2.10.4.
