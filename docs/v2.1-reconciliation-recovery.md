# V2.1 Reconciliation & Recovery

Reconciliation is the safety mechanism for ambiguous external side effects.

## Contract

`UNKNOWN` delivery is never treated as proof that nothing happened.

```text
publish
  -> ambiguous result
  -> UNKNOWN
  -> reconcile
       -> CONFIRMED: confirm
       -> NOT_FOUND: safe retry until max attempts
       -> UNKNOWN: defer and reconcile again
```

## Recovery policy

- `CONFIRMED` is terminal success for delivery.
- `NOT_FOUND` permits a safe retry only while the attempt budget remains.
- exhausted retries fail the execution while preserving `UNKNOWN` delivery state for audit/review.
- `UNKNOWN` is deferred; it is never converted directly into a retry.
- backoff is exponential and capped.

## Ownership boundary

Recovery actions that can mutate publication state (`CONFIRM`, `SAFE_RETRY`, `FAIL`) require the current worker identity and an unexpired worker lease. This matches the existing V2.1 execution engine contract, which operates with `workerId` and `lease_expires_at` and rejects completion when lease ownership is invalid.

`DEFER` is safe without ownership because it does not perform a recovery mutation.

The reconciliation module validates the ownership facts supplied by the execution layer; it does not implement or replace the database claim/heartbeat functions.

## Deliberate scope

This PR defines deterministic classification, ownership preconditions, and backoff. It does not implement a reconciliation worker, provider API calls, scheduling, rate limiting, or credentials.
